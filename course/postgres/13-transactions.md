# Урок 13. Транзакции и уровни изоляции

## Цель

После урока студент сможет: группировать операции в атомарные транзакции (BEGIN/COMMIT/ROLLBACK, SAVEPOINT), объяснять ACID «своими словами» и понимать уровни изоляции READ COMMITTED vs SERIALIZABLE (границы «честности»).

## Теория

Транзакция — логическая единица работы: «либо всё, либо ничего» + «внешним выглядит атомарно». Команды: BEGIN; ... COMMIT; (успех) / ROLLBACK; (откат). Без явного BEGIN каждая команда — «авто-транзакция» (отдельный COMMIT).

SAVEPOINT — «закладка» внутри транзакции: ROLLBACK TO sp; откатывает до закладки, но не всю транзакцию. Для «попробовать операцию, не уронило всё».

ACID: Atomicity (всё/ничего), Consistency (схема+ограничения до и после), Isolation (параллельные транзакции «не мешают» в пределах уровня), Durability (после COMMIT — данные на диске, даже при падении).

Уровни изоляции (SQL-стандарт; PG поддерживает 4):
- READ COMMITTED (по умолчанию): видно только COMMIT-нутое; «чтение без недочитов», но возможны «несогласованные чтения» между двумя SELECT'ами в одной транзакции (первый запрос — данные до UPDATE чужой, второй — после).
- REPEATABLE READ: снапшот на момент первого запроса — внутри транзакции «мир застыл»; редкая сериализационная аномалия → ошибка 40001 (сервер откатывает транзакцию — повторный запуск обязателен).
- SERIALIZABLE: полная «последовательность», как если бы транзакции шли по очереди; цена — частые конфликты (40001).
- READ UNCOMMITTED — в PG работает как READ COMMITTED.

Классические аномалии: dirty read (чужой не-commit-нутый UPDATE), non-repeatable read (пересчитал значение — оно изменилось), phantom (появились новые строки в том же «окне»).

## Пример

```sql
-- сессия A:
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- ... (ещё не COMMIT)

-- сессия B (READ COMMITTED):
SELECT balance FROM accounts WHERE id = 1;   -- ещё старое значение (A не COMMIT-нул)

-- сессия A:
SAVEPOINT sp1;
UPDATE accounts SET balance = balance + 10 WHERE id = 2;
ROLLBACK TO sp1;                              -- вторая операция «не случилось»
COMMIT;                                       -- первая операция — зафиксирована

-- сессия B:
SELECT balance FROM accounts WHERE id = 1;   -- теперь новое (COMMIT был)

-- смена уровня изоляции на сессию:
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE; -- на ближайший BEGIN
```

## Частые ошибки

WARN: «Долгая транзакция» с сетевыми вызовами внутри (HTTP, очередь) — блокировки держатся секунды-минуты, другие сессии ждут; в REPEATABLE READ/SERIALIZABLE — ещё и «старый снапшот» раздувает WAL. Транзакция = только DB-операции.

WARN: Забыл ROLLBACK в ошибочном пути (или EXCEPTION в приложении) — «висит» open transaction: \dt показывает «idle in transaction», другие сессии блокируются.

WARN: Ожидал REPEATABLE READ «везде по умолчанию» — по умолчанию READ COMMITTED: два SELECT в транзакции могут увидеть РАЗНЫЕ данные (вторая сессия COMMIT-нула между ними). Для «отчёта по срезку» — явный уровень.

WARN: Сервер вернул 40001 (serialization_failure) — это НЕ «баг», а нормальный исход SERIALIZABLE/RR: перехвати и повтори транзакцию (с экспоненциальным backoff).

TIP: `\dt` в сессии показывает блокировки; для мониторинга — `SELECT * FROM pg_stat_activity WHERE state = 'idle in transaction'`.

## Практическое задание

1. Две psql-сессии в базе practice. Создай `accounts (id PK, balance NUMERIC(10,2))` (2 строки по 1000).
2. Сессия A: BEGIN; переведи 100 с id=1 на id=2 (2 UPDATE). Без COMMIT — сессия B: `SELECT * FROM accounts` (старые значения). COMMIT в A; пересмотри в B.
3. Повтори, но в A используй SAVEPOINT: второй UPDATE «откатись» до SAVEPOINT (останется только перевод).
4. Сессии A: `BEGIN ISOLATION LEVEL SERIALIZABLE`; B: параллельные UPDATE одной строки — кто-то получит lock-wait (поставь `SET lock_timeout = '2s'` в B и зафиксируй ошибку).
5. Ответь письменно: почему READ COMMITTED не спасает от «несогласованного отчёта» (2 SELECT в одной транзакции)?
