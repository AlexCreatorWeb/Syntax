# Урок 3. CREATE TABLE: ограничения и identity-колонки

## Цель

После урока студент сможет: спроектировать таблицу с правильными ограничениями (PRIMARY KEY, NOT NULL, UNIQUE, CHECK, DEFAULT), понимать генерацию ID (SERIAL vs GENERATED AS IDENTITY), описывать ограничения на уровне колонки и таблицы, читать сообщения об ошибках ограничений.

## Теория

Ограничение (constraint) — правило, которое СУБД гарантирует сама: приложение не может вставить «плохую» строку. Виды:

PRIMARY KEY — «это кто»: уникальность + NOT NULL в одном. Одна PK на таблицу. Тип: BIGINT identity или UUID (урок 2).

NOT NULL — «обязательно значение». Без него колонка может быть NULL (особенность SQL: NULL — не «пусто», а «неизвестно», сравнивать её надо через IS NULL — урок 6).

UNIQUE — уникальность по колонке (набор колонк): email, телефон, SKU. Отличие от PK: может быть NULL (NULL не считается дубликатом), можно несколько.

CHECK — произвольное условие: `price_cents >= 0`, `status IN ('new','sent')`. Вычисляется при вставке/обновлении; нарушение = ошибка 23514.

DEFAULT — значение, если колонку не указали: `DEFAULT now()`, `DEFAULT 'draft'`.

Генерация ID. Старый способ: `id SERIAL PRIMARY KEY` (под капотом — sequence). Современный ANSI-стандарт: `id BIGINT GENERATED ALWAYS AS IDENTITY` (вставка в id не допускается; GENERATED BY DEFAULT — допустима). identity «роднее» таблицы (виден в \d, нельзя случайно скопировать sequence на другую таблицу).

Ограничения «на уровне таблицы»: `CONSTRAINT имя UNIQUE (a, b)` — именованные ограничения дают читаемые ошибки («violates unique constraint accounts_email_key») — именование: `name_` + описание. Именованный CHECK: `CONSTRAINT orders_total_check CHECK (total_cents >= 0)` — в тексте ошибки будет `orders_total_check`, а не автогенерированное `orders_total_cents_check`.

Совет по проектированию: пиши ограничения «мелко» (одно условие — один CHECK) — тогда ошибка точно укажет, что именно сломалось.

## Пример

```sql
CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_email TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'new' CHECK (status IN ('new', 'paid', 'shipped', 'canceled')),
    total_cents INT NOT NULL CHECK (total_cents >= 0),
    placed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT orders_email_unique UNIQUE (customer_email)
);

INSERT INTO orders (customer_email, total_cents) VALUES ('a@b.c', 1000);
INSERT INTO orders (customer_email, total_cents) VALUES ('a@b.c', 2000);  -- ошибка: unique
INSERT INTO orders (customer_email, status, total_cents) VALUES ('x@y.z', 'lost', 5); -- ошибка: check
SELECT * FROM orders;
\d orders   -- ограничения видны в секции «Indexes» и «Check constraints»
```

## Частые ошибки

WARN: «Уникальность проверяем в коде» — гонка двух запросов вставляет дубли до того, как код заметит. UNIQUE-ограничение на уровне БД — единственный честный способ.

WARN: Забыл NOT NULL у обязательного поля — потом не можешь добавить его: строки с NULL уже лежат (сначала заполнить default, затем ALTER ... SET NOT NULL).

WARN: CHECK-условие с NULL: `CHECK (age > 0)` НЕ ловит NULL (NULL > 0 = unknown, а не false). Если значение опционально, но «если есть — валидно» — это ок; если обязателен и валидный диапазон — CHECK + NOT NULL.

WARN: SERIAL в мигровочных инструментах и рефакторинге «разваливается» (sequence отдельный объект). Для новых схем — GENERATED AS IDENTITY.

TIP: Имя ограничения = таблица_столбец_тип: orders_email_unique. Ошибка «violates check constraint orders_status_check» сразу указывает, что сломалось — в проде это экономит минуты.
