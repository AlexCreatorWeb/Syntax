# Отладка: поиск и исправление багов

## Цель

После урока студент сможешь: объяснить, как Claude Code ищет баги, сформулировать задачу «найди и исправь баг» так, чтобы агент не ушёл не туда, использовать логи и стектрейсы как вход для агента, и понимать, какие баги агент находит хорошо, а какие — плохо.

## Теория

Отладка с агентом — это не «агент найдёт баг сам». Это структурированный процесс: ты даёшь агенту симптом (что сломалось, где, как воспроизвести), агент ищет причину, предлагает исправление, ты проверяешь. Качество отладки — это качество симптома, который ты дал.

Хороший симптом: «в функции X при вводе Y падает TypeError: Z. Стектрейс: ...». Плохой симптом: «что-то не работает». Стектрейс — это подарок для агента: он сразу видит, где падает, и может прочитать этот файл. Без стектрейса агент тратит итерации на разведку. Ещё лучше — скриншот или лог из консоли браузера: агент «видит» состояние, в котором баг проявляется, и ему проще гипотетизировать.

Процесс отладки с агентом: (1) даёшь симптом, (2) агент читает файлы из стектрейса, (3) агент hypothesizes причину (модели хорошо гипотетизируют), (4) агент предлагает исправление, (5) ты проверяешь (запускаешь тест или воспроизводишь сценарий), (6) если не сработало — даёшь новый симптом. Цикл повторяется, пока баг не найден. Держи счётчик итераций: если три цикла без результата — вероятно, симптом неполный, и стоит добавить контекст, а не продолжать «в лоб».

NOTE: агент хорошо находит «локальные» баги: ошибка в одной функции, опечатка, пропущенная валидация. Хуже — «распределённые» баги: состояние, которое накапливается через несколько функций, гонки, тайминги. Для распределённых багов агенту нужно больше контекста: логи, порядок вызовов, что было до ошибки. Чем больше контекса дашь — тем лучше агент гипотетизирует.

Есть и приём «бинарный поиск по коммитам»: если баг появился «где-то в последние 20 коммитов» — попроси агента сделать git bisect: он будет проверять коммиты пополам, запуская тест на каждом, и за логарифмическое число шагов найдёт, в каком коммите баг появился. Это работает для багов, которые ловит тест.

TIP: держи в CLAUDE.md раздел «Отладка»: где логи, как их читать, какие инструменты ( debugger, console.log, тесты). Тогда агент знает, куда смотреть, и не тратит итерации на «как у вас логи устроены».

Есть и приём «баг в тест»: если баг воспроизводится стабильно — попроси агента сначала написать тест, который его ловит (красный тест), и только потом чинить. Красный тест — это и критерий успеха (после фикса он зелёный), и страховка от регрессии (баг не вернётся). Для багов, которые «иногда», это сложнее: сначала нужно воспроизвести, и тут помогают логи и детерминированные условия (фиксированные данные, отключённые таймеры).

## Пример

```bash
claude

# Даем симптом со стектрейсом
> в функции parseUser при пустом email падает:
> TypeError: Cannot read properties of undefined (reading 'trim')
>   at parseUser (src/utils/parse.js:42)
> Найди причину и исправь

# Агент:
# 1. читает src/utils/parse.js
# 2. видит: user.email.trim() — но email может быть undefined
# 3. предлагает: if (!user.email) return null;
# 4. правит файл
# 5. запускает npm test

# Проверяем: тесты зелёные, баг исправлен
```

В примере видно: стектрейс → агент сразу видит место → гипотетизирует → правит → проверяет. Быстро и предсказуемо.

## Частые ошибки

WARN: «что-то не работает» без деталей: агент тратит итерации на разведку. Дай симптом: что сломалось, где, как воспроизвести, стектрейс (если есть).

WARN: не проверять исправление: агент «исправил» ≠ баг ушёл. Запусти тест или воспроизведи сценарий. Объективная проверка > доверие.

WARN: один баг за сессию: если багов несколько — лучше разбить на задачи. Один баг = один цикл отладки = чёткий критерий успеха.

WARN: не давать контекст для распределённых багов: без логов и порядка вызовов агент гипотетизирует вслепую. Чем больше контекста — тем точнее гипотеза.

## Практическое задание

В файле CLAUDE.md (открыт в редакторе) зафиксируй свой процесс отладки: где логи, как их читать, какие инструменты используешь. Заполни разделы по шаблону и устрани все TODO. И помни: отладка — это не «агент угадал», а «симптом + контекст + проверка». Три элемента, и ни одного лишнего. Чем точнее симптом, тем меньше итераций, и тем быстрее баг становится историей.
