# Лучшие практики: что реально работает (опыт 500 часов)

## Цель

После урока студент сможет: назвать 5–7 практик, которые реально экономят время при работе с Claude Code, избежать типичных антипаттернов, и выстроить собственный рабочий процесс, который масштабируется от маленьких задач до больших фич.

## Теория

Лучшие практики — это не «мнение экспертов», а паттерны, которые подтверждены сотнями часов реальной работы. Ниже — то, что действительно работает, а не то, что красиво звучит.

Практика 1: маленькие задачи. Не «сделай фичу аутентификации», а «добавь функцию hashPassword и тесты». Маленькая задача — это чёткий критерий успеха, короткий цикл, лёгкий откат. Большие задачи распадаются на маленькие, и ты выполняешь их по одной. Это не микроменеджмент модели — это инженерия задач.

Практика 2: CLAUDE.md как фундамент. Если CLAUDE.md хороший, агент «знает» проект и тратит меньше итераций на разведку. Если CLAUDE.md пустой — каждый запуск начинается с нуля. Инвестиции в CLAUDE.md окупаются с первого же запуска.

Практика 3: git-дисциплина. Commit перед каждым крупным изменением. Branch для каждой фичи. Это не про «чистую историю» — это про способность откатить агента к любому состоянию. git reset --hard — твой главный инструмент контроля.

Практика 4: читай, что агент делает. Цикл прозрачен, но если ты не смотришь — пропустит, что агент пошёл не туда. Первые 10 секунд каждого запуска: какие файлы читает, какие команды запускает. Если ушёл не туда — останови и поправь.

Практика 5: тестируй результат, а не процесс. Не «агент всё сделал правильно?», а «проходят ли тесты?». Критерий успеха — не «агент закончил», а «тесты зелёные, команда X выдаёт Y». Объективный критерий снимает споры.

Практика 6: «проект-песочница». Заведи отдельный маленький репозиторий, где можно экспериментировать с агентом без страха: новые режимы, хуки, MCP-серверы. В основном проекте эксперименты дороги (можно сломать), в песочнице — дёшевы. Когда эксперимент удался — переносишь настройку в основной проект.

Практика 7: читай документацию модели, а не только доки инструмента. Раз в месяц выходит новая версия модели, и поведение может меняться (лучше следит за инструкциями, иначе тратит токены). Пять минут чтения release notes экономит часы догадок «почему агент вдруг стал иначе работать».

NOTE: лучшие практики — это не догма. Для каждого проекта и каждой задачи баланс меняется. На новом проекте — строгие разрешения, маленькие задачи, много git-коммитов. Когда понял, как агент работает — можно ускориться: большие задачи, auto-accept, меньше коммитов. Практики — это стартовая точка, а не финальная.

Отдельно про окружение: Claude Code работает лучше в «чистом» окружении. Если у тебя в проекте 20 веток, грязный git-статус и сгенерированные файлы, которые агент может случайно «починить» — сначала приведи в порядок: коммиты, .gitignore для артефактов, чистая ветка. Агент отлично работает в аккуратном репозитории и часто путается в грязном: не понимает, что «моя» правка, а что «чужая».

TIP: веди «дневник агента»: что сработало, что нет, какие формулировки задач дали хороший результат. Через 2–3 недели у тебя будет личный набор паттернов, который работает именно на твоём проекте. Это бесценно — его нельзя купить, только накопить.

## Пример

```bash
# Практика: маленькие задачи + git-дисциплина
git checkout -b feature/refresh-tokens

# Маленькая задача 1
> добавь функцию hashPassword в src/lib/auth.ts и тест

# Проверяем результат
npm test
git add -A && git commit -m "add hashPassword"

# Маленькая задача 2
> добавь issueRefreshToken и rotateRefreshToken

npm test
git add -A && git commit -m "add refresh token functions"

# Если что-то пошло не так — откат
git reset --hard HEAD~1
```

В примере видно: маленькие задачи, commit после каждой, тесты как критерий успеха. Это и есть рабочий процесс.

## Частые ошибки

WARN: «одна большая задача»: агент тратит итерации на разведку, ты не видишь, где он ушёл не туда, откатывать нечего. Маленькие задачи — это контроль.

WARN: CLAUDE.md на потом: если CLAUDE.md пустой, каждый запуск начинается с нуля. Инвестируй в CLAUDE.md с первого дня.

WARN: нет git-коммитов: если агент «сломал» проект, откатывать не от чего. Commit перед каждым крупным изменением — не опция, а необходимость.

WARN: не читать результат: «агент закончил» ≠ «всё работает». Запускай тесты, проверяй критерий успеха. Объективная проверка > доверие.

## Практическое задание

В файле CLAUDE.md (открыт в редакторе) зафиксируй свой рабочий процесс: как ты разбиваешь задачи, когда делаешь commit, какой критерий успеха используешь. Заполни разделы по шаблону и устрани все TODO.
