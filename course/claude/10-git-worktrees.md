# Git и параллельная работа с Claude Code

## Цель

После урока студент сможет: объяснить, что такое git worktree и зачем он нужен, настроить параллельную работу нескольких агентов на разных задачах, избежать конфликтов и выбрать, когда параллельность оправдана, а когда — нет.

## Теория

Проблема: один агент, одна ветка, одна задача. Если ты хочешь работать над двумя задачами параллельно (одна — в фоне, вторая — активно), они конфликтуют: агент меняет файлы, которые ты тоже меняешь, git-статус становится грязным, коммиты перемешиваются.

Решение: git worktree. Worktree — это несколько рабочих каталогов, привязанных к одному репозиторию. Каждый каталог — это отдельная ветка, и изменения в одном не влияют на другой. Ты запускаешь одного агента в worktree A (ветка feature/login), второго — в worktree B (ветка feature/search). Они работают параллельно, не мешая друг другу.

Как настроить: git worktree add ../project-login feature/login создаёт каталог ../project-login с веткой feature/login. Внутри этого каталога запускаешь claude — и агент работает в изолированной среде. Когда задача готова — merge'ишь ветку в основную и удаляешь worktree. Все зависимости (node_modules, .env) в каждом worktree свои: это плюс (изоляция) и минус (установка зависимостей в каждом каталоге заново).

Когда параллельность оправдана: задачи независимые (разные модули, разные файлы), и ты хочешь «запустить и забыть» одну, работая над другой. Когда не оправдана: задачи зависят друг от друга (одна меняет то, что использует другая), или задачи маленькие (настройка worktree дороже, чем выгода).

NOTE: worktree — это не магия. Если две задачи меняют один и тот же файл, при merge'е будет конфликт — как и с обычными ветками. Worktree снимает проблему «грязного git-статуса в одном каталоге», но не проблему «две ветки меняют одно место». Планируй параллельность по независимым модулям.

Есть нюанс с сессиями: каждая сессия Claude Code живёт в своём каталоге и не знает о соседних. Если задача в worktree A требует контекста из main (например, «как устроена аутентификация» — а аутентификация в main) — агент в worktree A не увидит это, если код не закоммичен в ветку worktree. Поэтому перед запуском параллельных задач main должен быть актуальным и закоммиченным.

TIP: держи naming convention для worktree: ../project-<task-name>. Тогда всегда понятно, какой каталог для какой задачи. И держи в CLAUDE.md список активных worktree, чтобы не запутаться, где какая задача.

Удобный приём — «worktree на задачу, commit на шаг». Внутри worktree ты всё равно делаешь коммиты по мере готовности: так откатывается не вся задача, а конкретный шаг. А когда задача готова — merge в main, squash или обычный merge по вкусу, и git worktree remove. Через неделю у тебя будет аккуратная история: каждая фича — отдельная ветка с понятными коммитами.

## Пример

```bash
# Основная ветка — main, работаем в ./project
cd project

# Создаём worktree для задачи «login»
git worktree add ../project-login feature/login

# Запускаем агента в worktree
cd ../project-login
claude
> реализуй login по email (см. CLAUDE.md)

# В основной ветке — вторая задача
cd ../project
claude
> добавь поиск по названию (см. CLAUDE.md)

# Обе задачи работают параллельно
# Когда готовы — merge:
git merge feature/login
git worktree remove ../project-login
```

В примере видно: две задачи, два каталога, два агента — параллельно, без конфликтов.

## Частые ошибки

WARN: параллельность зависимых задач: если одна задача меняет то, что использует вторая — при merge'е будет конфликт. Параллельно — только независимые модули.

WARN: забыть удалить worktree: worktree живёт до тех пор, пока не удалишь. git worktree remove — после merge. Иначе каталоги копят.

WARN: один git-каталог на две задачи: без worktree изменения перемешиваются, git-статус грязный, коммиты конфликтовать. Worktree решает это.

WARN: параллельность для маленьких задач: настройка worktree (создать каталог, запустить агента, merge, удалить) дороже, чем просто сделать задачу последовательно. Параллельность — для больших независимых задач.
