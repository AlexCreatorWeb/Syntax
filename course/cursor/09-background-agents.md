# Background Agents: облачные агенты и PR

## Цель

После урока студент сможет: объяснить, чем облачный агент отличается от локального, запустить фоновую задачу в облаке Cursor, следить за её статусом и принять результат как pull request — с тем же контролем качества, что и работу коллеги.

## Теория

Локальный агент работает, пока открыт редактор и включён ноутбук. Облачный (Background) агент — другой контур: ты описываешь задачу, Cursor поднимает в облаке выделенную среду (собственный checkout твоего репозитория, зависимости, терминал), агент работает там самостоятельно — и результат возвращается pull request. Ты можешь закрыть ноутбук, уехать, спать: агент «не ждёт, пока ты вернёшься к экрану». Это сдвиг от «агент помогает мне печатать» к «агент — ещё один член команды, у которого свой график».

Цикл: (1) формулируешь задачу (с того же «контекст — цель — критерий», что локально — уроки 8); (2) выбираешь ветку/базу (обычно main); (3) агент в облаке: читает репозиторий (и .cursorrules — правила проекта попадают в облако вместе с кодом), делает правки, запускает команды (тесты, сборку — если в репо есть package.json со скриптами), (4) открывает PR с описанием и диффом; (5) ты: читаешь дифф (как в уроке 8), оставляешь комментарии или принимаешь. Если агент «завис» или уехал — в логе сессии видно, что он делал; задачу можно «подвинуть» сообщением (агент продолжит с учётом) или остановить.

За что облачный агент хорош, а за что — нет. Хорошо: задачи с чётким критерием на 30 минут–2 часа («напиши unit-тесты для модуля формы», «переведи весь контент на второй язык», «добавь адаптивность под мобильные»). Плохо: задачи, которые требуют твоего решения по ходу («как тут лучше, вариант А или Б?»), и мелочь (одна строка — облачный запуск медленнее, чем Ctrl+K). И не надо: задачи, которые «поменяют половину репозитория» — это проект, а не задача (разбивка — урок 18).

Параллельность — главная фича. Пока облачный агент делает адаптивность, локальный агент в редакторе делает контент, а ты пишешь текст. Три «работника» параллельно — и ни один не ждёт другого. Главное правило параллельной работы — границы: у каждого агента своя область (свой файл, свой каталог, своя ветка), чтобы диффы не пересекались. Пересечение областей = конфликты слияний = потеря времени.

PR — это «контракт» с облачным агентом. Агент не «исправляет репо напрямую» (нет force-push'ей и прямых коммитов в main) — он предлагает. Это принципиально: приёмка через PR даёт (1) полное окно для диффа, (2) возможность «переговоров» с агентом (комментарии → агент дорабатывает), (3) историю: каждый PR — задокументированная единица работы. Привычка «PR = чья-то работа, которую я ревьюю» — переносится один в один с тимлидом.

TIP: держи в репозитории package.json с понятными скриптами (npm test, npm run build, npm run lint): облачный агент видит их и запускает «сам по себе». Без скриптов агент либо не проверит результат, либо запустит «что-то своё» — и твои критерии останутся на бумаге.

NOTE: облачные агенты — платная надстройка (в Pro/Teams-тарифах, с учётом лимитов): точные цифры и имена функций смотри в актуальных доках Cursor. Логика цикла (задача → среда → работа → PR → ревью) от тарифа не зависит.

## Пример

```bash
# Сценарий «вечер»: три задачи параллельно.
# 1. Облачный агент: «Напиши Vitest-тесты для validateForm() в main.js;
#    критерий: npm test зелёный, покрыты пустое поле и не-email».
#    (задача ушла в облако — ноутбук можно закрыть)
# 2. Локальный агент: «Обнови цены в menu.json на новые (список приложен)».
# 3. Ты: пишешь тексты для секции «О нас».

# Утром: облачный агент открыл PR. Проверяем:
git fetch origin
git log --oneline origin/agent/add-form-tests -3

# В PR: дифф (новые тесты), логи npm test (зелёный), описание по критериям.
# Ревью: файлы = только тесты + package.json (devDep vitest) — ок.
git merge
```

Смотри на приёмку: файлы (только то, что обещано), тесты (зелёные в логах), описание (по критериям). Три «да» — merge. Это и есть «агент-коллега».

## Частые ошибки

WARN: закидывать в облако «мелочь» или «полпроекта»: облачный запуск — 30 минут–2 часа, чёткий критерий. Мелочь — медленнее локального, проект — без критерия. Диапазон задач, где облако выигрывает, уже, чем кажется.

WARN: параллельные агенты без границ: «один — CSS, другой — тоже CSS» = конфликт слияний. Правило: один агент — одна область (файл/каталог/ветка). Если задачи переплетаются — запускай последовательно.

WARN: принимать PR «по названию»: «Add form tests» — и merge, не читая дифф. Название — обещание, дифф — факт. 30 секунд чтения диффа спасают от «агент добавил тест, который всегда зелёный» (тест-заглушка).

WARN: не давать агенту «руки» для проверки: без npm test в скриптах агент «сделал и забыл» — без обратной связи критерии не работают. Скрипты в package.json — половина качества облачной работы.

## Практическое задание

Заполни в .cursorrules раздел «Облачные агенты»: (1) список задач по «Зерну», которые подходят на облако (2–3 штуки, с критериями); (2) правило границ — как ты разделяешь области между параллельными агентами; (3) чек-лист приёмки PR (3 пункта: файлы, проверка, описание).
