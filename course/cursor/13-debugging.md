# Отладка: поиск и исправление багов

## Цель

После урока студент сможет: объяснять «петлю отладки» в Cursor (воспроизвести → сузить → гипотеза → минимальное исправление → проверить), пользоваться отладочными инструментами (консоль, MCP-браузер, Bugbot) и перестать «чинить вслепую» — менять код и надеяться.

## Теория

Отладка с ИИ — не «вставь ошибку в чат и жди». Это петля, и каждый её виток дешевле, чем «надежда». Петля: воспроизвести → сузить → гипотеза → минимальное исправление → проверить. Разбор.

Воспроизвести. Баг, который не воспроизвести, — не баг, а «проблема» (и её не чинить, а исследовать). Вопрос агенту: «Воспроизведи: какие шаги приводят к ошибке?» — и сам повторяешь (или через MCP-браузер: агент кликает по шагам). Результат — «рецепт»: «открыть страницу, заполнить email пустым, нажать отправить → TypeError в консоли». Рецепт — фундамент: без него «починка» = лотерея.

Сузить. «Где живёт баг?» — в каком файле, в какой функции, на какой строке. Инструменты: (1) консоль браузера (стектрейс — первые 2–3 строки укажут файл); (2) MCP-браузер (агент читает консоль сам — урок 10); (3) @Codebase + текст ошибки (агент семантически ищет «где обрабатывается submit»). Результат — «подозреваемый» (файл + функция), а не «проект в целом».

Гипотеза. «Почему?» — одна фраза: «валидация не проверяет пустую строку», «обработчик вешается до загрузки DOM», «цена парсится как строка, а сравнивается как число». Гипотеза — проверяемое утверждение, а не «что-то не то». Агент помогает: «Смотри на [функцию] — вот что может быть» — и ты выбираешь одну (не пять сразу!).

Минимальное исправление. Чиним ровно то, что в гипотезе: одну строку, одно условие. Не «пока переделаю валидацию целиком». Минимальность — потому что «большая» правка = новый дифф = новые потенциальные баги (и приёмка по диффу, урок 8, превращается в «читать половину модуля»).

Проверить. Трехуровневая приёмка (урок 12): npm test (уровень 1), браузер через MCP (уровень 2: «рецепт» из шага 1 больше не приводит к ошибке?), дифф (уровень 3: ровно то, что в гипотезе). И — регресс-тест: «добавь тест, который ловит этот баг» (урок 12) — иначе баг вернётся.

Инструменты поверх петли. (1) Консоль браузера — «глаза» (стектрейс, ошибки, логи). (2) MCP-браузер (Playwright) — «руки» (агент сам повторяет шаги, читает консоль, скриншотит). (3) Bugbot — ревью PR: агент-«рецензент» читает дифф и ловит «потенциальные баги» до merge (работает на PR — урок 9; для облачных агентов — встроенный рецензент). (4) @Codebase + текст ошибки — «карта» (где это устроено). (5) git bisect — «археолог» (баг появился в N-м коммите: git bisect поможет найти какой именно — для больших проектов).

Привычка: баг = задача для агента (с формулой «контекст — цель — критерий», урок 8): «Контекст: TypeError в validateEmail, рецепт — пустое поле. Цель: найти причину и поправить минимально. Критерий: npm test зелёный + рецепт не воспроизводится + тест-регресс добавлен». Одна формула — и петля работает «на автомате».

TIP: держи в .cursorrules «протокол отладки» (5 строк: воспроизвести → сузить → гипотеза → минимально → проверить + тест-регресс). Агент «знает» протокол — и не уходит в «чинить вслепую» (менять код и надеяться).

NOTE: «чинить вслепую» (поменять строку и посмотреть) — иногда работает (и это нормально для 30-секундных багов). Но для багов, которые «не чинятся» (второй, третий виток) — только петля: вслепую не чинится, потому что вслепую не видно причину.

## Пример

```bash
# Сценарий: «форма не отправляется, в консоли TypeError».
# 1. Рецепт (сам + MCP-браузер):
#    «Открыть /, email пустым, Submit → TypeError: Cannot read
#     properties of undefined (reading 'trim')»
# 2. Сузить: стектрейс → validateEmail() в main.js, строка 42.
# 3. Гипотеза: «value.trim() вызывается, когда value === undefined
#    (input не найден по id)».
# 4. Минимальное исправление (агент):
#    «В validateEmail: если !input — return false (с console.warn)».
# 5. Проверка: npm test (зелёный) + MCP-браузер (рецепт: без ошибки,
#    поле подсвечено) + дифф (одна функция) → коммит.
# 6. Регресс: «Добавь тест: validateEmail с пустым DOM — не падает».
```

Смотри на размер правки: одна функция, одна строка логики. Не «переделал валидацию». Это и есть «минимальное исправление».

## Частые ошибки

WARN: «чинить вслепую»: поменять строку, посмотреть, поменять другую. Для 30-секундных багов — ок; для «не чинится» — петля (воспроизвести → сузить → гипотеза → минимально → проверить).

WARN: сразу «большая» правка: «пока переделаю весь модуль». Минимальное исправление = маленький дифф = приёмка по диффу (урок 8) остаётся возможной. «Большая» правка = новый набор багов.

WARN: чинить без регресс-теста: баг «исправлен» — и вернётся через неделю (агент «улучшит» функцию и уберёт фикс). Тест, который ловит баг, — половина починки.

WARN: верить «агент нашёл причину» без проверки гипотезы: агент «предлагает» причину (иногда — правую, иногда — правдоподобную). Проверка гипотезы — минимальный эксперимент («если это причина — то X должно быть»). Без проверки — «чиним не то».
