# MCP: подключение внешних инструментов

## Цель

После урока студент сможет: объяснить, что такое MCP (Model Context Protocol) и зачем Cursor (и другие ИИ-среды) к нему подключаются, настроить свой первый MCP-сервер и сформулировать правило «какие инструменты — в MCP, а какие — в правилах/скриптах».

## Теория

MCP (Model Context Protocol) — открытый протокол, который описывает, как ИИ-агент разговаривает с внешними инструментами: база данных, браузер, Figma, Slack, Jira, файловое хранилище — что угодно, зачём агенту нужны «руки» за пределами репозитория. До MCP каждый редактор/чат имел свой формат «плагинов для агента» (у Cursor — свои расширения, у Claude — свои, у чата — свои); MCP унифицировал: один сервер, один протокол — и работает во всех клиентах, которые MCP поддерживают (Cursor, Claude Desktop, VS Code и другие).

Архитектура простая: MCP-сервер — это маленький процесс (на Node, Python, Go — что угодно), который по протоколу объявляет: вот мои инструменты (функции с именем, описанием, параметрами) и вот мои ресурсы (данные). Клиент (Cursor) показывает этот список агенту; агент сам решает, когда вызвать инструмент — например, «запроси у Figma последний вариант макета» или «создай тикет в Jira». Для агента MCP-инструмент выглядит как ещё одна функция: с именем, описанием и аргументами.

Что реально подключают (и стоит ли). (1) База данных (Postgres/SQLite): агент читает данные и схему — вместо «скопируй дамп в чат». (2) Браузер (Playwright и аналоги): агент сам ходит по твоему сайту, кликает, скриншотит — это «живая» проверка результата (урок 12, тестирование). (3) Дизайн (Figma): макет → агент берёт реальные размеры/цвета, а не «на глаз». (4) Задачи (Jira/Linear/GitHub Issues): агент создаёт/закрывает тикеты по ходу работы. (5) Скриншоты/аналитика: инструменты, которые «приносят данные» в контекст. Критерий подключения: инструмент, которым ты пользуешься чаще, чем раз в неделю, и для которого «скопировать руками» уже боль.

Настройка в Cursor: в настройках — раздел MCP (или глобальный файл mcp.json в формате «серверы: имя → команда запуска»). Типичный запись: имя, команда (npx имя-пакета или путь к скрипту), параметры (ключи API). После сохранения сервер поднимается, и его инструменты появляются в списке, который видит агент. Проверка: «@MCP (или список инструментов) — какие инструменты доступны?» — и попроси агенту вызвать один (например, «покажи список таблиц» для Postgres-сервера).

Где MCP не нужен. Если «инструмент» — это просто текстовое знание (доки, правила, примеры) — это не MCP, а @Docs/правила (уроки 6–7). Если это разовая команда в терминале — агент и так запускает команды. MCP — для «рук и датчиков» (действие/данные), а не для «знаний».

TIP: начинай с одного «скучного» сервера (Postgres или Playwright) и проверь его на реальной задаче дня. MCP-экосистема соблазняет «подключить всё» — но каждый сервер в списке инструментов = агенту чуть сложнее выбирать. Инструменты — как функции: чем их больше, тем выше шанс «не того» вызова.

NOTE: MCP-экосистема растёт быстро: появляются реестры публичных серверов, стандарты аутентификации, streamable-транспорт. Формат записи mcp.json и набор полей может меняться от версии Cursor — принцип «сервер = инструменты + ресурсы, агент сам выбирает, когда вызвать» — постоянный.

## Пример

```bash
# Подключаем Playwright-сервер (браузер для агента) — типовой пример:
# В настройках MCP (mcp.json) — запись:
# {
#   "mcpServers": {
#     "playwright": {
#       "command": "npx",
#       "args": ["@playwright/mcp@latest"]
#     }
#   }
# }

# После сохранения — сервер поднят. В чате:
# «Список доступных MCP-инструментов»
# «Открой http://localhost:5173 и скриншотни секцию меню»
# «Кликни по кнопке «Заказать» и скажи, куда перешла страница»

# Проверка, что сервер жив (в логах MCP):
# статус: connected, инструменты: browser_navigate, browser_click, …
```

Сценарий «Зерно»: агент правит секцию меню → через Playwright MCP сам открывает preview, кликает, скриншотит и показывает результат. Ручная проверка «открой браузер, глянь» — исчезает из цикла.

## Частые ошибки

WARN: подключать «всё из реестра»: 20 серверов = 200 инструментов в контексте = агент путается и «не того» выбирает. Правило: инструмент — если пользуешься чаще раза в неделю.

WARN: тащить «знания» в MCP: доки/правила/примеры — это @Docs и .cursorrules, а не сервер. MCP — для действий и данных (руки/датчики), не для головы.

WARN: не проверять инструменты после подключения: «записал в mcp.json — работает». Проверка — три секунды: «какие инструменты доступны» + один реальный вызов. Сервер, который не поднимается (нет зависимостей, нет ключа), молча «не там».

WARN: давать агенту опасные инструменты без ограничений: MCP-сервер с «удали таблицу» или «отправь письмо» — без ограничений = агент «оптимизирует» и отправит письмо не туда. Инструменты — с минимальными правами (read-only, где возможно).
