# Cursor Rules (.cursor/rules): правила проекта

## Цель

После урока студент сможет: объяснить, что такое Cursor Rules и зачем они нужны, различать четыре типа правил (всегда, по запросам агента, по шаблонам файлов, вручную), создать файл правил для проекта и перестать повторять в каждом промпте одно и то же.

## Теория

Правила (Rules) — это «память проекта» для ИИ. Без них каждый запрос начинается с нуля: «мы делаем лендинг, на чистом HTML/CSS/JS, без фреймворков, без тёмных тем, подписи на русском». С правилами эти факты пишутся один раз — и попадать в контекст каждого запроса автоматически. Разница ощутима сразу: агент перестаёт «гадать» про стек и стиль, и ответы становятся прикладными.

Физически правила — это markdown-файлы. В текущих версиях Cursor их кладут в каталог .cursor/rules/ (файлы с расширением .mdc, с фронтематтером в начале: description, globs — к каким файлам правило применяется, alwaysApply — применять всегда ли). Легаси-вариант — один файл .cursorrules в корне проекта: он до сих пор поддерживается, проще (без фронтематтера) и лучше подходит для небольших проектов — им мы и пользуемся на курсе: весь курс наращиваем один файл .cursorrules. Для больших команд — каталог из нескольких файлов с globs (отдельные правила для CSS, отдельно для JS, отдельно для контента).

Четыре типа правил (независимо от физического формата): (1) always — применяются ко всем запросам: стек, стиль кода, «не трогать сгенерированное»; (2) по шаблонам файлов (globs) — срабатывают, когда агент правит файлы, подпадающие под шаблон: правило «в CSS — только переменные, без hex в правилах» включается при правке *.css; (3) по запросу агента — агент сам решает, что ему нужно (он видит описание правила и «зовёт» его, если релевантно); (4) вручную — вставляются в чат через @-упоминание, когда правило нужно разово. На практике в .cursorrules живёт тип 1 (всё сразу), а в каталоге .cursor/rules — все четыре.

Что писать в правилах: факты, а не мечты. «Стек: HTML, CSS, JS (ES2020), без фреймворков» — факт, агент его выполняет. «Сделай сайт красивым и удобным» — мечта, агент её интерпретирует по-своему. Хорошие правила — это конструктор из коротких утверждений: про стек, про структуру (какие файлы за что отвечают), про стиль (названия классов, форматирование), про контент (язык, тон), про запретное («не использовать alert», «не удалять секции без спроса»). Плохие правила — длинные абзацы «о духе проекта»: агент держит в голове последние, а не первые строки.

Объём — важная дисциплина. Файл правил на 30–80 строк — норма: он читается человеком и целиком попадает в контекст. Файл на 500 строк начинает конкурировать с самим кодом: агент «забывает» середину, а человек уже не перечитывает. Правило: если правило не применялось две недели — вынеси его из always (в ручной тип или в @docs — урок 7).

TIP: правила — это код, а значит — их версионируют: .cursorrules (и .cursor/rules) должны лежать в git. Команда читает правила как любой конфиг: с diff'ом, с историями правок, с ответственностью.

NOTE: в разных версиях Cursor интерфейс правил немного меняется (имена полей фронтематтера, способы «звать» правило по имени): принцип четырёх типов и «факты, а не мечты» — постоянные. Если в актуальной сборке что-то называется иначе — логика та же.

## Пример

```bash
# Каталог правил (для команды) vs файл проекта (наш курс):
# Команда:  .cursor/rules/style.mdc   (globs: ["*.css"], alwaysApply: false)
# Команда:  .cursor/rules/js.mdc      (globs: ["*.js"])
# Наш курс: .cursorrules в корне (тип always, весь курс наращиваем его)

# Проверить, что файл правил виден редактору:
cat .cursorrules

# Типичный запрос после правил (в чате):
# «Добавь секцию галереи» — без оговорок «на чистом CSS» и «на русском»:
# они уже в .cursorrules, агент их видит.
```

Сравни два промпта. Без правил: «Сделай галерею, у нас чистый HTML/CSS/JS, без бубнов, карточки 3 в ряд, подписи по-русски, не ломай вёрстку меню». С правилами: «Добавь секцию галереи». Второй промпт короче, потому что первые 3 строки — уже живут в файле.

## Частые ошибки

WARN: писать «мечты» вместо фактов: «сайт должен быть премиальным» агент выполнит по-своему — и каждый раз по-разному. Факты: «палитра — #2A211C, #C8A27A, #F5EFE6; шрифты — Playfair Display + Inter» — вот что агент выполнит одинаково.

WARN: раздувать always-файл до сотни строк: к 150-й строке агент начинает «не замечать» середину файла, а человек — его не читать. Правило двух недель (не применялось — вынести) держит файл живым.

WARN: держать правила локально и не коммитить: новый член команды (или облачный агент — урок 9) начинает с чистого контекста. Правила в git — часть репозитория, не часть «моей машины».

WARN: дублировать правила в промптах: «и не забудь, у нас чистый CSS, без бубнов» — если это уже в правилах, промпт дублирует контекст и тратит токены. Проверяй: факт в правилах? Тогда в промпте — только уникальное.

## Практическое задание

Перепиши раздел «Правила» в .cursorrules в формате коротких фактов: стек (3 строки), структура проекта «Зерно» (какие файлы и за что), стиль (названия классов, формат), контент (язык, тон), запретное (что агенту нельзя). Ограничь себя 15–25 строками — больше не надо. Убери TODO: с этого урока каждый запрос к Cursor по проекту начинается с этих фактов.
