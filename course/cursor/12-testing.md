# Тестирование с Cursor

## Цель

После урока студент сможет: объяснить три уровня проверки результата в Cursor-рабочем процессе (агент «сам проверяет», браузер через MCP, автотесты в проекте), настроить базовый набор автотестов с помощью агента и выстроить цикл «задача → проверка → приёмка».

## Теория

«Агент сделал» — не «агент сделал правильно». Между этими состояниями стоит проверка. В Cursor-процессе проверки живут на трёх уровнях, и каждый закрывает свой тип ошибок.

Уровень 1 — агент «сам проверяет». После правок агент может (и должен) запустить то, что запустить можно: npm test, npm run build, npm run lint — и прочитать вывод. Это «самодисциплина агента»: не «сделал и забыл», а «сделал и проверил». Настройка: в .cursorrules — правило «после правок в X — запускай Y» (урок 6); в package.json — понятные скрипты (урок 9). На этом уровне ловятся синтаксические ошибки, сломанные импорты, упавшие тесты — «механика».

Уровень 2 — «живой» браузер через MCP (Playwright, урок 10). Агент сам открывает preview, кликает, скриншотит, читает консоль. Это проверка «видит ли пользователь то, что должен видеть»: секция на месте? кнопка кликается? форма валидируется? Консоль без ошибок? Без этого уровня ловится класс «тесты зелёные, а в браузере — пустая страница» (JS-ошибка, которую не покрывает юнит-тест). Для лендинга «Зерно» это главный уровень: сайт — то, что видят люди, а не то, что видит тест-раннер.

Уровень 3 — автотесты в проекте (unit-тесты). Это «страховка на будущее»: когда проект растёт, ручные проверки и «скриншот агента» не масштабируются — нужны тесты, которые гоняются при каждом коммите. Для «Зерно» (статический лендинг) достаточно лёгкого набора: (1) тесты на «чистые» функции (валидация формы, генерация цен, фильтрация меню) — это то, что ломается чаще всего и что легко покрыть; (2) smoke-проверка структуры HTML (все секции на месте, все якоря существуют) — один тест, который ловит «агент случайно удалил секцию». Инструмент: Vitest (JS) — лёгкий, без настройки «на час».

Цикл. Задача (агент) → правки → уровень 1 (npm test/build — агент сам) → уровень 2 (браузер через MCP: скриншот + клики) → приёмка (ты: дифф + скриншот) → коммит (урок 11). Каждый уровень дешевле следующего: синтаксис ловится в 1, «видимость» — в 2, «регресс на будущее» — в 3. Пропуск уровня 1 ради 2 — «дорого и медленно».

Роль третьего уровня часто недооценивают: «у нас маленький проект, зачем тесты». Тесты нужны не «когда проект станет большим», а «чтобы агент мог работать без твоего постоянного контроля». С тестами агенту можно доверить «большую» задачу (он сам проверит, не сломал ли старое); без тестов — только «маленькую» (потому что старое проверишь только ты).

TIP: держи «тест-чек-лист» в .cursorrules: «после правок в main.js — npm test; после правок в HTML — открыть preview и проверить секции». Два правила — и агент «сам» проходит уровни 1–2 на 80% задач без напоминаний.

NOTE: для «чистого» фронтенда без бэкенда (как «Зерно») уровень 2 (браузер) важнее уровня 3 (юнит-тесты): сайт «живёт» в браузере. Для бэкенд-модулей — наоборот: юнит-тесты — основа, браузер — проверка интеграции.

## Пример

```bash
# Настройка уровня 3 (агент делает по задаче):
# «Добавь Vitest: тесты для validateEmail() и checkMenuStructure();
#  скрипт npm test; критерий — npm test зелёный».

npm test
# → validateEmail: пустое — false, "a@b.c" — true, "a@" — false (3 passed)
# → checkMenuStructure: секции hero/menu/gallery/contacts на месте (1 passed)

# Уровень 2 (MCP-браузер, урок 10):
# «Открой http://localhost:5173, проверь: секция меню на месте,
#  кнопка «Заказать» ведёт на #menu, консоль без ошибок»
# → скриншот + «ok: 4 секции, якорь работает, console clean»

# Приёмка: дифф (урок 8) + скриншот + npm test → коммит (урок 11).
```

Смотри на приёмку: три «да» (тесты, браузер, дифф) — и коммит. Один «нет» — назад (revert + уточнить задачу, урок 11).

## Частые ошибки

WARN: «тесты зелёные» как единственный критерий: юнит-тесты не видят браузер. Для фронтенда уровень 2 (живой браузер) обязателен — иначе «тесты зелёные, страница пустая».

WARN: не давать агенту «руки» для проверки: без npm test и MCP-браузера агент «сделал и забыл» — проверка только твоя (руками, в браузере). Скрипты + MCP = проверка «встроена» в цикл.

WARN: писать тесты «на всё подряд»: для лендинга достаточно «чистых» функций + smoke-проверки структуры. Покрытие 100% — не цель (дорого и медленно); цель — «то, что ломается, покрыто».

WARN: принимать «скриншот агента» без диффа: скриншот — «как выглядит сейчас», дифф — «что изменилось». Два взгляда, два вопроса: «правильно выглядит?» и «не сломал ли старое?».

## Практическое задание

Заполни в .cursorrules раздел «Тесты»: (1) три уровня — что ты делаешь на каждом (для «Зерно»); (2) тест-чек-лист (после правок в X — запускаешь Y); (3) список «чистых» функций проекта, которые будешь покрывать (2–3 штуки). Убери TODO: в уроке 13 (отладка) этот цикл станет «петлёй поиска багов».
