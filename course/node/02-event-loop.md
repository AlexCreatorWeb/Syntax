# Урок 2. Event Loop: фазы, макротаски и микротаски

## Цель

После урока студент сможет: объяснить, как устроен Event Loop и почему I/O в Node не блокирует код, отличать макротаски (setTimeout, I/O) от микротасок (queueMicrotask, Promise.then), предсказывать порядок вывода асинхронного кода и понимать, чем «зависает» Event Loop (блокирующие вычисления).

## Теория

### Как обрабатываются задачи

У Event Loop есть две «очереди»:

1. **Макротаски** (macro tasks) — следующий «круг» цикла: `setTimeout`/`setInterval`, I/O-операции (файлы, сеть), `setImmediate`.
2. **Микротаски** (micro tasks) — выполняются **сразу после** текущей задачи и **до** следующего макротаска: `queueMicrotask()`, `Promise.then/catch/finally`.

Порядок в каждом круге: выполнить одну макротаску → **опустить всю очередь микротасок** (даже те, что появились внутри них) → отрисовка (в браузере) → следующий круг.

Почему это важно:

- `setTimeout(fn, 0)` — **не** «сразу», а в следующем круге цикла (минимум ~1 мс + очередь);
- `promise.then(fn)` — раньше любого setTimeout, даже с 0;
- `await` внутри async-функции — «уходит» в микротаски.

### Неблокирующий I/O

Когда вы вызываете `fs.readFile`/`http.request`, ваш код **не ждёт**: вызов уходит в libuv (там — пул потоков для файлов, epoll/kqueue для сети), а в Event Loop попадает **задача-колбэк** на потом. Пока идёт I/O, основной поток свободен и обслуживает другие запросы.

**Блокирует** Event Loop только **CPU-тяжёлый синхронный код**: большой цикл, `fs.readFileSync` на огромном файле, тяжёлый `JSON.parse`. Пока он крутится — никто не обслуживается (сервер «замирает»).

### Как читать порядок вывода

Алгоритм: (1) прогоните синхронный код до конца (включая `console.log`), (2) микротаски (then/await) — до конца очереди, (3) макротаски по таймерам/I/O. Потренируйтесь «в голове» на примерах — это экзаменационный навык Node-интервью.

TIP: для «почти сразу, но после текущего кадра» — `queueMicrotask`; для «на следующем круге» — `setImmediate`; `setTimeout(…, 0)` — историческая замена, но медленнее и «грязнее» по семантике.

NOTE: в песочнице платформы (браузер) таймеры и промисы работают так же, как в Node; `setImmediate` в уроках не используется, чтобы не вводить в заблуждение (в браузере его нет).

## Пример

`server.js`:

```js
console.log("1: sync");

setTimeout(() => console.log("5: setTimeout 0 (макротаска)"), 0);
setTimeout(() => console.log("6: setTimeout 100"), 100);

queueMicrotask(() => console.log("4: queueMicrotask (микротаска)"));

Promise.resolve()
  .then(() => console.log("3: promise.then (микротаска)"))
  .then(() => console.log("3b: следующий then"));

async function main() {
  console.log("2: async до await");
  await Promise.resolve(); // «уход» в микротаски
  console.log("2b: async после await");
}
main();
// main() запускается синхронно до await, потом «вешается»
```

Ожидаемый порядок: `1, 2, 3, 3b, 4, 2b, 5, 6`.
Объяснение: sync-код (1, 2) → микротаски: then-цепочка (3, 3b), microtask (4), продолжение main (2b) → макротаски: setTimeout 0 (5), setTimeout 100 (6).

## Частые ошибки

WARN: ждёте, что `setTimeout(fn, 0)` выполнится «прямо сейчас». Это макротаска — следующий круг цикла; все микротаски (then/await) выполнятся **раньше** него.

WARN: блокируете Event Loop тяжёлым циклом (например, `while` на миллион итераций с синхронным `fs.readFileSync` внутри). Сервер «зависает» для всех запросов. Тяжёлые вычисления — в worker_threads или асинхронными чанками.

WARN: путаете `await` с «паузой всей программы». `await` останавливает только **текущую async-функцию**; остальной код (и другие запросы) продолжается.

WARN: думаете, что микротаски «выполняются раз в круг на одну». Нет: очередь микротасок **полностью** опустошается (включая новые) перед следующим макротаском.

## Практическое задание

1. Напишите скрипт, который выводит в этом порядке: `sync` → `then` → `microtask` → `await-продолжение` → `setTimeout 0` → `setTimeout 50`. Используйте `Promise.resolve().then`, `queueMicrotask`, `async/await` и два `setTimeout`.
2. Смените местами `queueMicrotask` и `promise.then` — предскажите новый порядок и проверьте.
3. Добавьте `await new Promise(r => setTimeout(r, 20))` в async-функцию и выведите что-то после — убедитесь, что это произошло позже `setTimeout(…, 0)` из п.1.
4. Запустите в платформе (**Run**) и в терминале — сравните порядок.
5. Мини-эссе (1 абзац в комментариях кода): почему `await` не блокирует Event Loop.
