# Code review: ревью PR с Copilot

## Цель

После урока студент сможет: объяснить, что делает Copilot code review (автоматическое ревью pull request), запустить его на PR taskit (от агента или от себя), прочитать и «переварить» комментарии ревью (отличить баг от вкусовщины), и собрать свой чеклист «ревью PR с ИИ» (что читать до, что после).

## Теория

Copilot code review — фича на стороне GitHub: при открытии pull request (или по кнопке «@copilot review») GitHub запускает анализ диффа: модель читает изменения, смотрит контекст (файлы, тесты), и оставляет комментарии — как человек-ревьюер: на строки, с пояснением. С 2025-м в ревью добавили CodeQL (статический анализ) и «агентов» для глубинных проверок — ревью стало многослойным: и модель (логика), и CodeQL (классы багов), и агент (глубокий анализ).

Почему ревью от ИИ — отдельный навык (а не «ещё один комментатор»): ИИ-ревью оставляет два типа комментариев. Первый — «реальные» (баг, гонка, утечка, неверная обработка null/None): они ценны и часто ловят то, что человек упустил. Второй — «вкусовщина» («можно было бы использовать list comprehension», «назови переменную по-другому»): они не баги, и если принимать все — устанешь править то, что не сломано. Навык урока — разделить эти два типа и реагировать по-разному: на первый — правка (или аргументированный «зачем так»), на второй — «заметили, поправим в рефакторинге» или «так оставим».

Механика: в PR → вкладка «Conversation» → кнопка «@copilot» (или «Request review from Copilot») → через 1–3 минуты комментарии. Можно «перезапустить» ревью (если поправил код). В новых версиях — «review agents» для специфичных проверок (безопасность, доступность).

Чеклист «ревью PR с ИИ» (что делать):

- До ревью: прочитай диф сам (хотя бы бегло) — чтобы комментарии ИИ были «вторым мнением», а не «первым».
- Запусти @copilot review (и, если есть, CodeQL-ревью).
- Прочитай комментарии, раздели на «баг» / «вкусовщина» (две колонки в голове).
- На «баг»: поправь (сам или попроси агента в PR) или аргументируй.
- На «вкусовщину»: примешь только то, что реально упрощает; остальное — «закрыть как noted».
- Прогони тесты локально (ревью не заменяет тесты).
- Merge (только если всё выше — зелёное).

TIP: для PR от Coding Agent (урок 7) ревью — обязательный шаг: агент «сдаёт» PR, и единственная точка контроля — дифф + ревью + тесты. Без ревью ты мержишь «на доверии», а доверие к агенту — до первой выдуманной функции.

NOTE: качество ИИ-ревью растёт от релиза к релизу: в одних версиях больше «вкусовщины», в других — больше реальных багов. Не калибруй ожидания на одном PR: посмотри 3–5 ревью на разных диффах, и ты поймёшь «характер» твоей версии.

## Пример

```bash
# 1. Открой PR (от Coding Agent или свой):
gh pr view 12

# 2. Запусти ревью (в веб): кнопка «@copilot» в Conversation,
#    или через gh (если доступна в твоём тарифе):
#    gh pr review 12   # — свой ревью-комментарий, а не ИИ;
#    ИИ-ревью — через кнопку в веб-интерфейсе PR.

# 3. Прочитай комментарии. Раздели:
#    - «mark_done не обрабатывает task_id=None (TypeError)» → БАГ.
#    - «можно использовать f-строку вместо concat» → ВКУСОВЩИНА
#      (и к тому же мы и так используем f-строки — правило в инструкциях).

# 4. Поправь баг (коммент в PR → агент/ты правит),
#    вкусовщину — «noted, в рефакторинге». Прогони pytest. Merge.
```

Обрати внимание на момент 3: разделение «баг / вкус» — и есть навык. Без него ты либо «поверишь» ревью и поправишь 10 «не багов», либо «не поверишь» и пропустишь реальный баг.

## Частые ошибки

WARN: мержить PR без ревью (даже «маленький»): «маленький дифф» — не аргумент; агент в маленьком диффе может поменять поведение, которое не видно в 5 строк. Ревью + тесты — для каждого PR.

WARN: принимать все комментарии ревью: «вкусовщина» накапливается в «у нас стиль как у ИИ» — и через месяц проект будет «стилизован» чужими предпочтениями. Свой стиль — в copilot-instructions.md; ревью — на отклонения от него.

WARN: полагаться на ревью вместо тестов: ИИ-ревью читает дифф, тесты — исполняют код. Ревью скажет «здесь может быть None», тесты — «да, было, и вот как упало». Оба нужны, но тесты — первичны.

WARN: «спорить» с ревью без аргумента: коммент «зачем так?» без объяснения — не аргумент. Если не согласен — напиши, почему (ссылка на инструкцию, на тест, на кейс). Тогда и агент, и следующий ревьюер поймут решение.

## Практическое задание

Открой последний PR taskit (от Coding Agent из урока 7), запусти @copilot review, раздели комментарии на «баг / вкус» (запиши в issue или заметку), поправишь баги, прогонишь тесты, смержешь. Затем заполни в copilot-instructions.md раздел «Ревью PR»: правило «ревью на каждый PR», «баг — правим, вкус — noted», «тесты до merge», «комментарий без аргумента не принимается». Эти правила будут читать и ты (человек), и агент (при само-ревью).
