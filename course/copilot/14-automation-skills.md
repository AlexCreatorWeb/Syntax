# Автоматизация: Copilot + Actions, Custom Skills

## Цель

После урока студент сможет: объяснить, как Copilot встраивается в GitHub Actions (автоматическое ревью, CLI в CI), собрать минимальный workflow с Copilot-ревью для taskit, написать Custom Skill (папку с инструкциями для агента) и объяснить границу автоматизации (что автоматизируем, что оставляем человеку).

## Теория

GitHub Actions — CI/CD на стороне GitHub: workflow (YAML в .github/workflows/) запускает шаги на машине GitHub по триггеру (push, PR, расписание). Copilot в Actions — два слоя.

Слой 1 — «Copilot-джобы» в workflow: GitHub добавляет готовые джобы (Copilot Code Review — автоматическое ревью каждого PR, Copilot CLI — запуск CLI-агента в CI). Настройка — строка в YAML (steps с action: copilot/...), и каждый PR получает ревью без участия человека. Это «ревью по умолчанию»: человек смотрит то, что ИИ пропустил, а не наоборот.

Слой 2 — свой CLI в CI: copilot (урок 9) как обычный шаг workflow: «сгенерируй changelog», «проверь, что в PR есть тесты», «обнови README по диффу». Это тот же CLI, только на машине GitHub, и результат — коммент в PR или файл.

Custom Skills — «памятка» для агента (локального и облачного): папка в репозитории (например, .github/skills/changelog/), где лежит файл с инструкциями (SKILL.md) и, опционально, скрипты. Агент подхватывает skill по триггеру («напиши changelog» → skill changelog) и работает по инструкции. Зачем: «как мы делаем changelog» — один раз в skill, и каждый агент (локальный, облачный, в CI) делает одинаково. Skills — это «инструкции для конкретного вида задач», тогда как copilot-instructions.md — «инструкции для всего проекта».

Граница автоматизации (главное правило урока): автоматизируй то, где есть чёткий критерий (тесты прошли, ревью оставлено, changelog сгенерирован), и не автоматизируй то, где нужно решение (merge, смена архитектуры, «а может, не надо»). Auto-merge на «тесты зелёные» — ловушка: тесты зелёные, а решение неправильное. Merge — всегда человек (или, минимум, человек + ИИ-ревью).

И последнее: автоматизация — это «повторяющаяся рутина, которая устала быть рутиной». Если задачу ты делаешь руками второй раз — она кандидат в workflow/skill. Если первый — сделай руками, и только когда повторится — автоматизируй.

TIP: начни с одного workflow (Copilot-ревью на каждый PR) и одного skill (changelog). Два артефакта — и у проекта уже есть «автоматическое качество» (ревью) и «автоматическая рутинность» (changelog). Больше — по мере того, как увидишь, что повторяешь.

NOTE: Actions-джобы с Copilot считаются в «minutes» вашего репозитория (бесплатно для публичных — 2000 минут/месяц) и, для ИИ-частей, в premium-запросы. Не гоняй «тяжёлый» агент на каждый push — только на PR (и только один раз, а не на каждый коммит).

## Пример

```bash
# 1. Workflow с Copilot-ревью (.github/workflows/copilot-review.yml):
#    name: copilot-review
#    on:
#      pull_request:
#        types: [opened, synchronize]
#    jobs:
#      review:
#        runs-on: ubuntu-latest
#        steps:
#          - uses: actions/checkout@v4
#          - uses: github/copilot-review-action@v1   # имя сверь по докам

# 2. Push workflow → открой PR → через 2–3 минуты в PR
#    появятся комментарии от Copilot (без твоего «@copilot»).

# 3. Skill (папка .github/skills/changelog/SKILL.md):
#    «Из git log (последние N) сгенерируй блок changelog в формате:
#     ## [дата] — Added/Fixed/Changed. Пиши в CHANGELOG.md,
#     сверху, без удаления старых блоков.»
#    Запрос «напиши changelog» → агент подхватит skill.
```

После этого у taskit «работает само»: PR открывается → ИИ-ревью оставляет комментарии (человек смотрит), «напиши changelog» → skill генерирует. Два артефакта, два правила, и «рутина» перестала быть рутиной.

## Частые ошибки

WARN: auto-merge на «тесты зелёные»: тесты проверяют «работает ли», а не «правильно ли решили». Merge — человек (минимум: человек + ИИ-ревью + тесты). Auto-merge — только для «механических» PR (bump версии, Dependabot).

WARN: писать skill «на всё» (один SKILL.md на 20 задач): skill подхватывается по триггеру, и «всё» = «ничего конкретного». Один skill — один вид задачи (changelog, issue-шаблон, тест-кейсы).

WARN: гнать тяжёлого агента на каждый push: minutes и premium-запросы улетят. Триггеры: PR (один раз), push в main (если нужно), расписание (редко). Не «весь мир».

WARN: не читать workflow перед «пушем»: YAML с action: copilot/... — чужая программа, которая будет работать на машине GitHub. Прочитай, что она делает (checkout, какие секреты видит, какие права) — и только потом push.

## Практическое задание

Собери для taskit: (1) workflow copilot-review.yml (ревью на каждый PR) — проверь на реальном PR; (2) skill .github/skills/changelog/ (формат changelog для taskit) — проверь запросом «напиши changelog». Затем заполни в copilot-instructions.md раздел «Автоматизация»: какие workflow есть, что они делают, какие skills, правило «merge — человек», правило «тяжёлый агент — только на PR».
