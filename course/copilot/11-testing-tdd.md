# Тестирование: TDD и генерация тестов

## Цель

После урока студент сможет: объяснить цикл TDD (red-green-refactor) в связке с Copilot, попросить модель написать тесты до кода и довести их до «красного», отличить полезный тест от «тест-обёртки» (проверяет то, что и так работает), и собрать мини-процесс «тест → агент реализует → рефакторинг» на taskit.

## Теория

TDD — метод: сначала пишешь тест (он падает — red), потом пишешь минимум кода, чтобы тест прошёл (green), потом рефакторишь (чистишь, не ломая тесты). С Copilot цикл становится быстрее в обеих фазах: тесты генерируются за секунды, и реализация «под тест» тоже. Но появляется и главная ловушка курса: модель, которая пишет и тесты, и код, может написать тесты, которые «проверяют» собственную реализацию, а не задачу. Поэтому правило курса: тесты пишешь ты (или просишь модель и читаешь каждый), реализация — пусть агент.

Как просить тесты правильно (формулировки решают):

- «Напиши тесты для mark_done: неизвестный id → ValueError; уже выполненная задача → идемпотентно; пустой tasks.json → пустой список». Конкретные кейсы — конкретные тесты.
- «Какие edge-cases у list не покрыты тестами?» — аудит покрытия (модель читает код и тесты и называет дыры).
- «Переписи этот тест без моков» — чистка «тест-обёрток».

Что такое «тест-обёртка» (и как её узнать): тест, который дублирует реализацию («вызываю save(), проверяю, что файл записан тем же кодом, что и save()») — он пройдёт при любой реализации и упадёт только при сбое диска. Полезный тест проверяет контракт: «после add(«кофе») в list она есть». Контракт — из задачи (issue, docstring), а не из кода.

Роль Copilot в TDD-цикле (разделение труда):

- Red: ты задаёшь кейсы (или модель предлагает, ты проверяешь), агент дописывает тесты, pytest падает.
- Green: агент реализует минимум под тесты (Agent mode / coding agent).
- Refactor: «упрости, не ломая тесты» — модель рефакторит, тесты страхуют.

Этот цикл — «оправдание» всех предыдущих уроков: у агентов (локальных и облачных) теперь есть критерий «сделано». Без тестов агент «сдаёт» то, что не падает; с тестами — то, что работает.

TIP: держи «тестовый промпт» в copilot-instructions.md (раздел «Тесты»): какие кейсы обязателен каждый тест команды, как называть (test_<команда>_<кейс>), где лежат (test_taskit.py). Тогда и локальный агент, и облачный будут писать тесты по одному стандарту.

NOTE: pytest в курсе — потому что он стандарт де-факто в Python и его понимает каждый агент. Если в твоем проекте unittest/other — те же принципы, другая синтаксика. Главное — что тесты есть и агент знает, как их запускать (раздел «Команды»).

## Пример

```bash
# 1. RED: напиши тест ДО кода (в test_taskit.py, вручную или через чат):
#    def test_remove_unknown_id():
#        with pytest.raises(ValueError):
#            remove(99)
#    python -m pytest test_taskit.py::test_remove_unknown_id  → FAIL

# 2. GREEN: Agent mode: «реализуй remove так, чтобы тест
#    test_remove_unknown_id и другие тесты remove прошли».
#    Агент пишет минимум кода; pytest → PASS.

# 3. REFACTOR: «упрости remove и mark_done, не ломая тесты».
#    python -m pytest  → всё ещё PASS.
```

Обрати внимание на порядок: тест — контракт, код — под контракт. Если бы мы сначала написали remove (через комплит), а потом «добавили тесты» — тесты бы «подстроились» под реализацию, и catch-кейс (неизвестный id) мог бы не появиться.

## Частые ошибки

WARN: просить «напиши тесты» без кейсов: модель напишет «тесты для happy path» — и все они пройдут при любой реализации. Кейсы (вход/выход/ошибка) — в промпт.

WARN: принимать «тест-обёртки» как покрытие: 20 тестов, которые дублируют код — не 20% надёжности, а 0% (они упадут вместе с кодом). Проверка: «что сломается, если этот тест упадёт?» — если «ничего конкретное», тест-обёртка.

WARN: писать тесты и код одной правкой и не читать: TDD-цикл держится на том, что тест существует ДО кода. «Одновременно» — это уже не TDD, а «тесты для отчёта».

WARN: гонять агента «до зелёного» без чтения тестов: агент, который хочет «сдать», может поправить тест (смягчить ожидание), а не код. После каждого «зелёного» глянь дифф тестов — не только дифф кода.

## Практическое задание

Доведи команду search (из урока 8) до полного покрытия: напечатай 4–5 кейсов (попадание, нет попаданий, пустой запрос, регистр, несколько слов), через Agent mode доведи тесты до «красного» и «зелёного». Затем заполни в copilot-instructions.md раздел «Тесты»: где лежат, как запускать, стандарт имён, что обязателен для каждой команды (happy + error + edge), правило «дифф тестов читать вместе с диффом кода».
