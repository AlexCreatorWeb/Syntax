# MCP: внешние инструменты в Copilot

## Цель

После урока студент сможет: объяснить, что такое MCP (Model Context Protocol) и зачем он нужен (стандарт подключения внешних инструментов к ИИ-клиентам), подключить локальный MCP-сервер к VS Code с Copilot, объяснить разницу между MCP-инструментом и @workspace, и выбрать, когда MCP нужен, а когда достаточно чата.

## Теория

MCP — Model Context Protocol — открытый стандарт (от Anthropic, 2024), по которому ИИ-клиент (VS Code, Cursor, чат в браузере) подключает внешние инструменты: базы данных, файловой менеджер, поиск по документации, внутренние API. До MCP каждый клиент имел свой формат «допов» (плагины, API, SDK), и каждый сервис писал интеграцию под каждого клиента. MCP снял это: сервис пишет один MCP-сервер — и он работает во всех клиентах-поддерживающих протокол (VS Code с Copilot — среди первых).

Архитектура простая: MCP-сервер — отдельный процесс (Node/Python-скрипт), который объявляет «у меня есть инструменты X, Y, Z» (tool'ы) и «ресурсы A, B» (данные, которые модель может читать). Клиент (VS Code) показывает их в чате: @mcp или в списке инструментов, и модель вызывает их как обычные функции. Результат возвращается модели в контекст.

Что это даёт на практике:

- MCP-сервер PostgreSQL: модель сама пишет SELECT по твоей БД и видит строки — без ручного «а, глянь, вот вывод psql».
- MCP-сервер файловой системы: чтение/поиск файлов вне папки проекта.
- MCP-сервер документации: поиск по внутренней wiki/докам.
- MCP-сервер проекта: твой API (добавить задачу в taskit, проверить тесты) как инструмент.

Где живёт настройка: .vscode/mcp.json в папке проекта (серверы проекта) или пользовательские настройки (серверы на все проекты). Формат: имя сервера, команда запуска, аргументы, переменные окружения.

Когда MCP нужен, а когда нет: если инструмент — это «данные, которые модель должна видеть» (БД, доки, API) — MCP. Если «модель должна прочитать файл проекта» — @workspace уже делает это. Если «одна команда в терминале» — @terminal. MCP — для повторных, структурированных взаимодействий с внешним миром, а не для разовых «покажи вывод».

TIP: начни с одного «скучного» сервера (файловой или Postgres) и проверь его на вопросе, который без него решался в три шага (вышел в терминал, запустил, вставил вывод в чат). Разница «1 шаг против 3» — и ты понял ценность MCP.

NOTE: MCP-серверы — чужие процессы с доступом к твоим данным: сервер PostgreSQL видит твою БД, файловый — твою файловую систему. Перед установкой из маркета читай: какие инструменты объявляет, какие права просит, открыт ли исходник. «Мощный» сервер с закрытым кодом — тот же плагин из интернета, только с доступом к данным.

## Пример

```bash
# 1. Пример mcp.json (проект taskit, сервер «файловой системы»):
# .vscode/mcp.json:
# {
#   "servers": {
#     "fs": {
#       "type": "stdio",
#       "command": "npx",
#       "args": ["-y", "@modelcontextprotocol/server-filesystem",
#                "/home/user/projects/taskit"]
#     }
#   }
# }

# 2. Перезапусти VS Code (или иконка «reload» у MCP-панели).
#    В чате: @mcp — увидишь инструменты сервера (read_file, list_dirs...).

# 3. Спроси: «@mcp, какие файлы в проекте и какой у tasks.json размер?»
#    Модель вызовет инструменты fs — и ответит по данным сервера,
#    а не по памяти о проекте.
```

Сценарий намеренно «глупый» (файлы видно и без MCP) — чтобы почувствовать механику: модель вызвала внешний инструмент и ответила по его данным. Дальше те же механики на PostgreSQL и твоём API.

## Частые ошибки

WARN: подключать пять MCP-серверов «на всякий случай»: каждый сервер — инструменты в контексте, и каждый «конкурирует» с кодом за внимание модели. Держи 1–2 осознанных сервера, а не «весь маркет».

WARN: делать MCP «для одной команды»: если инструмент = «запустить pytest», это @terminal, а не сервер. MCP окупается на повторных, структурированных вызовах (БД, API, доки).

WARN: не читать, что сервер «видит»: fs-сервер с корнем /home — это доступ к всей твоей домашней. Ставь корень на папку проекта (как в примере) — и «случайный» вызов не прочитает лишнего.

WARN: путать MCP с плагином редактора: MCP-сервер живёт вне редактора (отдельный процесс) и работает во всех MCP-клиентах. Плагин — внутри редактора. Если «инструмент» нужен только в VS Code — плагин; если «данные/инструмент для ИИ» — MCP.

## Практическое задание

Подключи MCP-сервер (fs или Postgres — что ближе) к VS Code с проектом taskit, проверь три вопроса через @mcp и убери «на всякий случай» всё, что не используется (оставь один). Затем заполни в copilot-instructions.md раздел «Инструменты и MCP»: какой сервер подключён, какие у него инструменты, когда использовать его, а когда достаточно @workspace/@terminal. Это сохранит следующему (агенту, teammate) понимание «что тут подключено».
