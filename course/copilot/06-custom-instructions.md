# Кастомные инструкции (.github/copilot-instructions.md)

## Цель

После урока студент сможет: объяснить, что такое кастомные инструкции Copilot и где их искать (уровень проекта, уровень пользователя, уровень организации), написать файл .github/copilot-instructions.md, который реально улучшает ответы чата и агента, и отличить инструкции от README (кому что читать).

## Теория

Кастомные инструкции — это «памятка» для Copilot: текстовый файл, который GitHub подмешивает в контекст модели при каждом чате, комплите и агентской сессии. Ты пишешь его один раз — и модель ведёт себя по твоим правилам во всём проекте, без повторения «у нас стиль такой-то, команды такие-то» в каждом запросе.

Три уровня (иерархия, верхние дополняют нижние):

- Организация: repo settings → Copilot → instructions (бизнес-тариф, правила для всех репозиториев команды).
- Репозиторий: файл .github/copilot-instructions.md (и несколько файлов .github/instructions/*.instructions.md с условием applies-to — например, отдельные правила для тестов и для CI).
- Пользователь: ~/.copilot/copilot-instructions.md — личные правила, которые действуют во всех твоих проектах.

Файл урока — .github/copilot-instructions.md (в нашем редакторе он открыт как copilot-instructions.md). Правила написания:

- Маркдаун, plain text, 200 строк — комфортный потолок: длиннее — модель «устанет» и начнёт игнорировать хвост.
- Пиши утверждениями, как правила: «Тесты — pytest, запускаются командой python -m pytest», а не «мы бы хотели, чтобы тесты были написаны где-то».
- Порядок важности: сначала «как проверить, что всё работает» (команды), потом структура, потом стиль, в конце — «не трогай X».
- Что писать: стек и версии, команды запуска/тестов/линтера, структура (где что лежит), стиль (форматирование, имена, типизация), запреты («не добавляй зависимости без спроса», «данные — в tasks.json, не в SQLite»).
- Что не писать: всё, что и так видно из кода («используем Python» — это видно), длинную историю, философию.

Отличие от README: README читает человек (кто приходит в репозиторий), инструкции читает модель (кто пишет код в нём). README — «что это и как начать», инструкции — «как здесь принято и как проверить». У них есть пересечение (команды), но тональность разная: README — приглашение, инструкции — регламент.

TIP: пиши инструкции вместе с агентом: «вот наш проект, предложи draft copilot-instructions.md на 60 строк» — и правь его. Пустой файл пугает, а черновик от модели — нет; правка занимает вдвое меньше времени, чем написание с нуля.

NOTE: инструкции подмешиваются в контекст, а значит, едят его: при больших файлах и длинных чатах «конкурируют» с кодом. Держи файл компактным (до 200 строк), а редкие развёрнутые правила выноси в отдельные .instructions.md с applies-to — так они подхватываются только там, где нужны.

## Пример

```bash
# 1. Создай файл (структура уже готова в редакторе — допиши разделы):
mkdir -p .github
cp copilot-instructions.md .github/copilot-instructions.md

# 2. Проверь, что инструкция работает: открой чат (Ctrl+L) и спроси
#    БЕЗ упоминаний:
#    «как запустить тесты в этом проекте?»
#    Ожидаемо: python -m pytest — модель прочитала «Команды».
#    Без файла ответ был бы обобщённым («скорее всего, pytest»).

# 3. Проверь стиль: «напиши функцию add_task» —
#    ответ должен быть с type hints, f-строкой и docstring,
#    как в разделе «Стиль кода».
```

Сравнение «с файлом / без файла» — лучший учебный эксперимент курса: задай один и тот же вопрос в двух чатах (во втором — временно переименовав файл), посмотри на разницу в конкретных ответах. Это и есть измеримый эффект инструкций.

## Частые ошибки

WARN: писать «инструкцию-блог» на 500 строк: модель начинает пропускать хвост, и правило «не трогай тесты» (которое ты написал последним) игнорируется. 200 строк — потолок, 100 — комфорт.

WARN: дублировать код: «у нас функция save() делает X, Y, Z» — код меняется, инструкция гниёт, и модель начинает верить инструкциям вместо кода. Пиши правила, а не описание реализации.

WARN: держать файл только локально, не коммитить: инструкции живут в .github/ — это файл проекта, а не личная заметка. Без коммита у teammates (и у Coding Agent, который видит только репозиторий) её нет.

WARN: путать уровни: личные правила (например, «люблю 4 пробела») в .github/ — они затрут для всех; общие правила проекта в ~/.copilot/ — они затрут только для тебя. Личное — в home, проектное — в репозиторий.

## Практическое задание

Доведи copilot-instructions.md до полной версии «каркаса»: разделы «О проекте», «Команды», «Структура», «Стек», «Стиль кода» — все заполнены (уроки 1–5), добавь раздел «Работа со мной» (правила общения: отвечать на русском, короткие ответы, сначала план потом код, не добавлять зависимости без подтверждения). Проверь экспериментом из «Примера» (вопрос про тесты без упоминаний) — ответ должен совпасть с твоим разделом «Команды».
